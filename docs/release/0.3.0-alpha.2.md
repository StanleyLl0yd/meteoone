# MeteoOne 0.3.0-alpha.2

Maintenance test release of the self-contained Android M1-M4 product.
This supersedes the signed `0.3.0-alpha.1` test build; it does **not**
introduce a server, cloud backend, new permissions, new Room schema or M6 work.

## Changes since 0.3.0-alpha.1

- **Current conditions and offline cache (M3):** correctly select a forecast
  hour near the device's current clock time when reopening an older 72-hour
  Room snapshot; do not present the first historic hour as current, and do
  not fabricate current conditions from expired snapshots. Existing cached
  hourly/three-day forecasts remain available with freshness indicators.
  Reviewed and merged in [#295](https://github.com/StanleyLl0yd/meteoone/pull/295).
- **Verification samples (M4):** for temperature, pressure and wind, match
  the nearest *usable* GHCNh observation independently per parameter within
  the existing 30-minute hard bound. Preserve deterministic ties, QC and
  wind-vector semantics, including calm conditions. Reviewed and merged in
  [#292](https://github.com/StanleyLl0yd/meteoone/pull/292).
- **Build and security maintenance:** Gradle 9.8.1, Kotlin 2.4.21 and
  validated SHA-pinned GitHub Actions updates. Pinned Qodana full-tree scheduled
  run [38249200042](https://github.com/StanleyLl0yd/meteoone/actions/runs/38249200042)
  reported zero findings on the preceding exact main.

## Unchanged product guarantees

- Direct Android HTTPS forecasts from NOAA GFS, ECMWF IFS, DWD ICON,
  and Open-Meteo fallback/cross-check, fused hourly over 72 hours.
- On-device observation verification using GHCNh, exact model-run history,
  guarded independent model-family weights and equal-weight fallback for
  insufficient, stale, inconsistent or conflicting evidence.
- Room-first offline behavior, coarse/canonical 0.1-degree coordinates,
  no persisted precise device location, RU/EN UI and native arm64 ecCodes/JNI.
- No proprietary MeteoOne backend, server URL, server-side API or M6 code.

## Device acceptance for this build

1. Install **in place** over signed `0.3.0-alpha.1` without clearing
   application data; confirm versionCode 4 and retained Room/cache state.
2. Reopen a forecast cached 24-48 hours earlier while offline. Confirm the
   current-conditions card tracks a real point near current time rather than
   always showing hour zero; hourly/three-day pages remain accessible.
3. Reopen after the 72-hour forecast horizon has expired. Confirm the
   current-conditions card does not fabricate a present-day reading; cached
   history is clearly marked stale/expired.
4. Refresh online, check model attribution GFS/IFS/ICON and partial-failure
   behavior, then repeat offline force-stop/restart, reconnection and reboot.
5. Confirm approximate-location permission and RU/EN Settings/Forecast/Models.
   Never upload raw precise coordinates or identifying location logs.
6. Collect independent test/diagnostic evidence for sparse GHCNh per-parameter
   matching, guarded weight fallback and native direct-official ecCodes/JNI
   GRIB execution. **UI behavior alone cannot prove these internal paths.**
7. Complete at least 1-2 days of physical-device operation including
   connectivity changes, cache freshness, stability and battery observation.
   Link reproducible failures as issues. Do not mark an unobservable path PASS.

Extended device evidence remains tracked in
[#288](https://github.com/StanleyLl0yd/meteoone/issues/288).
No RuStore upload for this test version.

## Signing and distribution

GitHub prerelease only. `versionCode=4`, `versionName=0.3.0-alpha.2`.
The existing owner-authorized Signed Android Release workflow must first
verify successful CI, Security and Quality, Secret Scan and compiled CodeQL
on **exact canonical main**. It then builds/signs the APK and AAB together
using the existing Android signing identity, verifies APK v2/v3 and AAB
certificates plus required arm64 native libraries, and publishes exactly:

- `meteoone-0.3.0-alpha.2.apk`
- `meteoone-0.3.0-alpha.2.aab`

Preparing source metadata and these notes **does not publish** a signed
release. No release SHA, device acceptance, signing result or asset checksum
is claimed here before that workflow actually succeeds.

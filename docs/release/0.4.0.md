# MeteoOne 0.4.0

Android-only maintenance test release using **numeric-only** version names.
This replaces the previous signed M3/M4 maintenance test as the current
recommended installation. The earlier signed release/tag remains archived,
unchanged and traceable because its APK contains a distinct Android version.

## Changes

- Android `versionName` is `0.4.0` with `versionCode=5`. The monotonic
  version code allows installation over previous signed MeteoOne versions
  without discarding Room forecast history and cached settings.
- Enforce strictly numeric `major.minor.patch` for **new** releases in CI
  and release validation. Legacy tagged releases remain readable for
  provenance and monotonic version checks.
- GitHub prerelease metadata for 0.x.y test builds is independent of Android
  version names and Git tags.
- Inherits the prior build's M3 cached Current Conditions fix
  ([#295](https://github.com/StanleyLl0yd/meteoone/pull/295))
  and M4 nearest usable parameter-specific GHCNh observation matching fix
  ([#292](https://github.com/StanleyLl0yd/meteoone/pull/292)).
- Retains the audited Android 9.8.1 Gradle / Kotlin 2.4.21 toolchain
  and SHA-pinned CI, quality, supply-chain and native-bundle checks.

## Runtime and privacy

- Android directly retrieves NOAA GFS, ECMWF IFS, DWD ICON, and Open-Meteo
  fallbacks/cross-checks and generates its 72-hour hourly forecast locally.
- Local Room/DataStore offline cache, GHCNh observation verification,
  guarded independent model-family weights, and equal-weight fallback.
- Exact device location is not stored; forecasts use privacy-reduced
  0.1-degree coordinate identity. RU/EN user interface.
- On-device arm64 ecCodes/JNI decoder retained.
- **No MeteoOne backend, proprietary hosted service, server API or M6 work.**
- No new Android permissions or Room schema migrations in this release.

## Test focus

1. Upgrade in place from the previously signed test APK, keep application
   data, and verify `0.4.0` / `versionCode=5` plus Room/cache continuity.
2. Reopen stored forecasts offline, including 24-48 hour snapshots and
   expired 72-hour horizons; do not show a historical hour as live conditions.
3. Validate model comparison, 72-hour refresh, partial provider failure,
   reconnect, process restart, approximate location, and Russian/English UI.
4. Collect independent technical evidence for direct-official JNI decoding,
   usable GHCNh sparse-field matching and guarded dynamic weighting;
   UI smoke tests alone do not establish those internal paths.
5. Observe real-device stability, connectivity and battery for 1-2 days;
   report reproducible findings and keep unverified checks open.

Device acceptance remains tracked in
[#299](https://github.com/StanleyLl0yd/meteoone/issues/299)
and [#288](https://github.com/StanleyLl0yd/meteoone/issues/288).

## Release channel and signatures

Numeric version `0.4.0` is a **GitHub-only test build**, not a RuStore
production deployment. Its GitHub prerelease flag marks distribution status
without altering the numeric version string. Signed APK and AAB are built
from one verified canonical `main` SHA using the existing signing identity
and validated APK v2/v3 signatures, AAB certificate, and required arm64
libraries. Release assets must be exactly:

- `meteoone-0.4.0.apk`
- `meteoone-0.4.0.aab`

Publishing requires the existing owner-authorized signed-release workflow,
exact-main CI, CodeQL, Security and Quality, Secret Scan and version history
checks. Preparing this document is not proof that the binaries exist.

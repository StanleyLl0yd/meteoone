# MeteoOne 0.4.1

Android-only signed **maintenance diagnostic test release** for [#303](https://github.com/StanleyLl0yd/meteoone/issues/303). This is a GitHub prerelease, not a production-store deployment. The immutable [0.4.0 release](https://github.com/StanleyLl0yd/meteoone/releases/tag/v0.4.0) and its accepted functional-test results remain unchanged.

## What's changed

- Android `versionName=0.4.1`, `versionCode=6`, with the existing `com.sl.meteoone` application identity and signing policy. Intended for an in-place upgrade that preserves Room forecasts and settings.
- Adds the opt-in, manually initiated on-device M4 diagnostics from merged [PR #305](https://github.com/StanleyLl0yd/meteoone/pull/305). In Settings, **Run one diagnostic refresh** requests one forecast refresh and displays a transient, bounded aggregate report. Diagnostics do not run implicitly.
- Reports attempted provider/model pairs, real native ecCodes/JNI field decode successes, and whether successful official GRIB was used. An Open-Meteo fallback is not official GRIB evidence.
- Reports M4 exact-run attempt and stored history counts; selected GHCNh observation counts and per-parameter QC/matching sample counts; and guarded weight-policy decisions (`measured` or `equal_fallback` with reason category).
- Allows explicit **Copy sanitized report** for manual review. Diagnostic reports are neither persisted nor automatically uploaded; restarting the app discards them.
- Includes focused regressions for partial provider failure, missing observation evidence, invalid native data, cancellation, report reset/restart, and redaction/privacy guarantees.

No changes to forecast algorithms, providers, model-selection semantics, Room schema, device permissions, or M1-M4 product scope. **No MeteoOne backend, telemetry, exact coordinates in diagnostic output, or M6 implementation.**

## On-device acceptance: NOT YET VERIFIED

The goal is to collect independent evidence from **this exact signed 0.4.1 APK on a physical `arm64-v8a` Android device**. CI and host-side JNI tests cannot substitute for this step.

1. Obtain `meteoone-0.4.1.apk` only from the official release below; verify its published SHA-256 and installation/signing certificate. Prefer an in-place upgrade from signed 0.4.0 without clearing app data.
2. Confirm displayed app version `0.4.1`, ABI `arm64-v8a` and UTC diagnostic timestamp. Check an existing offline forecast/cache is still accessible.
3. Select a forecast location, open Settings and tap **Run one diagnostic refresh** while online. Wait for a completed refresh; a failed or cancelled refresh is not sufficient evidence.
4. Inspect actual provider/model attempts. To prove live official GRIB through bundled JNI, require an official NOAA/ECMWF/DWD attempt with `officialGrib=true` and `nativeDecodeSuccesses > 0` in the matching evidence. Fallback-only success must not be labeled official.
5. Inspect exact-run attempt and stored model/run entries, selected GHCNh observation counts, and per-parameter QC/matching sample counts. Zero counts must be interpreted as missing evidence, not a specific root cause.
6. Inspect the weight policy. `measured` is acceptable only with successful policy gates; `equal_fallback` must carry its reported reason and **must not** be presented as evidence of measured dynamic weighting.
7. Inspect the report for privacy before using **Copy sanitized report**. Attach only the safe aggregate text to [#303](https://github.com/StanleyLl0yd/meteoone/issues/303), preserving version, ABI and UTC timestamp. Never attach raw logs, coordinates, station IDs/positions, Room files, URLs, provider payloads or forecast-grid screenshots. Clear the report and clipboard afterwards.

Detailed procedure: [M4 device diagnostics](../verification/M4_DEVICE_DIAGNOSTICS.md).

Keep #303 **OPEN** until reviewed physical-device evidence meets the documented acceptance gate. Do not invent success or retroactively extend 0.4.0 acceptance.
